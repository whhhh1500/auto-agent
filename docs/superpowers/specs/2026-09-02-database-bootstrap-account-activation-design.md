# Database Bootstrap and Initial Account Activation Design

Date: 2026-09-02
Status: approved design, pending implementation

## Objective

Make a fresh Harness Core server self-bootstrapping while preserving explicit,
safe database selection:

- load configuration from a working-directory `.env` file;
- support explicit `sqlite` and `postgres` database types;
- default to SQLite when no database type is configured;
- create or repair the current SQL schema on connection;
- generate exactly one initial administrator only when the `accounts` table did
  not exist before migration;
- print that one-time account and password after successful persistence;
- require the generated administrator to change its password before the account
  becomes active; and
- complete at least three review/fix/verification rounds, each recorded under
  `docs/gaps`.

## Non-goals

- Do not generate an administrator merely because an existing `accounts` table
  is empty.
- Do not add database types beyond SQLite and PostgreSQL.
- Do not turn ordinary administrator password resets into first-login
  activation flows.
- Do not refactor unrelated runtime, capability, storage, or evaluation code.

## Configuration

The server loads `.env` from its current working directory before reading
configuration. Existing process environment variables take precedence. A
missing `.env` is allowed. A malformed file fails startup with a line-oriented
error that does not include secret values.

Supported variables:

```dotenv
HARNESS_DATABASE_TYPE=sqlite
HARNESS_SQLITE_PATH=./data/core.db
```

or:

```dotenv
HARNESS_DATABASE_TYPE=postgres
HARNESS_POSTGRES_DSN=postgres://user:password@host:5432/database?sslmode=require
```

Rules:

- An unset `HARNESS_DATABASE_TYPE` selects `sqlite`.
- The only accepted values are `sqlite` and `postgres`, case-insensitively after
  trimming whitespace.
- `postgres` requires a non-empty `HARNESS_POSTGRES_DSN`.
- `sqlite` rejects a configured `HARNESS_POSTGRES_DSN` instead of silently
  connecting to a different database.
- `HARNESS_SQLITE_PATH` remains optional and defaults to
  `<HARNESS_DATA_DIR>/core.db`.
- Production mode retains its current PostgreSQL and master-key safety
  requirements, except that initial administrator credentials are generated by
  the database bootstrap flow instead of supplied through
  `HARNESS_BOOTSTRAP_ADMIN_PASSWORD`.
- `.env.example`, README, deployment documentation, Docker Compose, and
  container defaults must describe the same selection rules.

## Database Inspection and Migration

After opening and pinging the selected database, the server checks whether the
`accounts` table exists before running schema initialization or migration. The
check supports both SQLite metadata and PostgreSQL catalog lookup.

The existing migration path remains authoritative and continues to execute
idempotent `CREATE TABLE IF NOT EXISTS` statements plus versioned column,
index, and projection migrations. A database missing tables, columns, or
indexes is repaired wherever the current migration contract already defines
the structure. Future schema versions continue to fail closed.

The pre-migration `accounts` existence result is carried into a dedicated
initial-account bootstrap operation. The operation uses a durable database
claim so concurrent fresh-server processes cannot create multiple initial
administrators. The claim is attempted only when the table was absent before
migration.

If the table existed before migration, the server never creates an initial
administrator, even when the table is empty. It starts normally without a
login-capable account.

## Account Model

The account identity is separated from optional contact information. The
current email-as-primary-key schema migrates to:

```text
account_id              TEXT PRIMARY KEY
email                   TEXT NULL
password_hash           TEXT NOT NULL
role                    TEXT NOT NULL
tenant_id               TEXT NOT NULL
status                  TEXT NOT NULL
must_change_password    INTEGER/BOOLEAN NOT NULL
created_at              BIGINT NOT NULL
```

`auth_tokens` refers to `account_id`. Existing accounts migrate as follows:

- `account_id` receives the old `email` value;
- `email` retains the old value;
- role, tenant, password hash, status, and creation time are preserved; and
- `must_change_password` is false.

The Go `Account` model exposes `AccountID` as identity and `Email` as optional
metadata. Principals, token ownership, session ownership, account limits,
audit actors, and administrative routes use `AccountID`. Email is not used as
an authorization identity.

The migration must be transactional for both supported dialects and must not
leave old and new account/token tables partially switched after an error.

## Initial Administrator

When and only when the pre-migration `accounts` table was absent, the winning
bootstrap process:

1. creates the `system` and `default` tenants idempotently;
2. generates an account ID in the exact form `admin_` plus five decimal digits;
3. retries boundedly if the generated ID collides;
4. generates a cryptographically random, high-entropy initial password;
5. creates the account with platform-admin role, `system` tenant,
   `pending_activation` status, empty email, and
   `must_change_password = true`; and
6. prints the account ID, one-time password, and an immediate-change warning
   only after the database transaction commits.

The credentials are printed once in dev, demo, and production modes. No later
restart may reconstruct or reprint the password. Failure before commit prints
no credentials. Logs must clearly label the password as a one-time sensitive
credential.

## Login and Activation

The canonical login request is:

```json
{"account":"admin_12345","password":"..."}
```

For a compatibility period the server also accepts the old `email` request
field as an account identifier when `account` is absent. Responses and new
documentation use `account`.

A valid pending-activation account may log in and receive a restricted bearer
token. Login returns `must_change_password: true`. Backend authorization, not
only the console, restricts that principal to:

- `POST /v1/auth/activate`; and
- `POST /v1/auth/logout`.

All other authenticated routes return HTTP 403 with the stable error
`account activation required`. Public health and readiness routes remain
available.

The activation request supplies a new password and confirmation. The password:

- is at least 12 characters;
- is bounded by the existing request and storage limits;
- contains no NUL;
- is not whitespace-only; and
- must differ from the initial password.

Activation hashes the new password, changes status to `active`, clears
`must_change_password`, revokes the restricted token and all other existing
tokens, and issues a new normal token. Password/status mutation and token
revocation are transactional. If final token issuance fails after commit, the
account remains safely active and can log in again with the new password; it
must never remain active with the old password.

Existing active and disabled accounts retain their behavior. The existing
administrator reset-password operation does not set
`must_change_password = true`.

## Console and API Contract

The console login form is relabeled from email to account. Account management
uses an account ID plus optional email. After a login response with
`must_change_password: true`, the console renders only an activation form and
does not fetch overview or administrative data. On successful activation it
stores the returned normal token and enters the overview.

The activation form requires the new password twice and reports validation and
server errors without displaying the initial or new password. Logout remains
available.

OpenAPI is updated for the canonical login field, activation endpoint, account
response fields, account administrative paths, optional email, pending status,
and the activation-required response. The embedded console verifier must show
that every console route is documented and every documented route exists.

## Error Handling and Security

- Unknown database types and contradictory database configuration fail before
  opening a database.
- Database connection and migration errors fail before HTTP listening.
- Schema inspection errors fail closed; they do not trigger bootstrap.
- A bootstrap claim or account creation error fails startup and prints no
  password.
- Generated credentials are never written to the database, file logs, audit
  details, session events, or API responses in plaintext beyond the explicit
  one-time process console output.
- Login retains constant-work unknown-account password verification and rate
  limiting.
- Pending tokens carry no broader capability through direct API calls,
  asynchronous work, runner routes, or administrative endpoints.
- Existing environment variables override `.env`, preventing a checked-out
  file from replacing deployment-injected secrets.

## Verification

Implementation tests cover:

- `.env` parsing, precedence, missing file, malformed input, and redacted
  errors;
- database configuration matrix and default SQLite selection;
- SQLite and PostgreSQL accounts-table preflight detection;
- missing-schema repair and future-version refusal;
- absent-table bootstrap, existing-empty-table non-bootstrap, concurrency,
  collision retry, persistence failure, and print-once behavior;
- legacy account migration and login compatibility;
- pending login, backend route denial, activation validation, transaction
  failure, token rotation, and active-account behavior;
- console activation gating and OpenAPI/route parity.

At least three independent review/fix/verification rounds follow the initial
implementation:

1. `docs/gaps/round-1-database-bootstrap.md` covers configuration, migration,
   bootstrap, concurrency, and restart behavior.
2. `docs/gaps/round-2-auth-activation.md` covers identity migration,
   authorization, activation, console, and API closure.
3. `docs/gaps/round-3-full-closure.md` covers whole-module regression, static
   checks, OpenAPI verification, and a real fresh-SQLite start/login/activate/
   restart smoke test.

Each report contains only: Scope, Findings, Fixes, Verification Evidence,
Remaining Risks, and Conclusion. Each round must inspect current code, fix its
findings, and re-run relevant verification; the reports cannot be three views
of one unchanged check.

Required final checks:

```text
go test ./...
go vet ./...
go run ./scripts/verify-openapi openapi/harness-core-v1.yaml pkg/server pkg/console/static/index.html
```

The SQLite runtime smoke uses a temporary directory and proves that credentials
print only on the first start, pending access is denied, activation succeeds,
and restart does not bootstrap again. PostgreSQL receives the same runtime
smoke when an actual local PostgreSQL or Docker environment is available; if
not, its absence is reported explicitly and is not represented as a pass.

## Completion Criteria

The work is complete only when the configuration, migration, initial-account,
activation, console, API, tests, documentation, three gap reports, and SQLite
runtime smoke all agree with this design; all required final checks pass; and
no unresolved high-priority closure issue remains.
