# Programmatic tool-calling fixture

The default executable is a deterministic protocol fixture. It uses a real `core.Runtime`, guarded capability calls, and a `ToolInvocationJournal` implementation local to the example. Its tools only return hard-coded read-only JSON; the executable makes no network or provider request. A separate, explicitly enabled live test is described below.

Run it from the repository root:

```powershell
go run ./examples/programmatic
```

The program executes two equivalent paths. The direct path lets a fixed model stub inspect the list result and choose each subsequent detail tool call. The programmatic path has a fixed model stub call `program.catalog`, select the two returned binding digests, and then call `program.execute`. Its JSON IR calls the inventory fixture, loops over its rows, branches on `active`, calls the detail fixture for matching rows, and returns one aggregate value. The stub's final turn reads that aggregate `program.execute` result.

The output compares model rounds, read-only fixture tool calls, protected journal invocations, model-visible message-history bytes, complete model-request JSON bytes, and final values. The request-byte value is the local `json.Marshal(GenerateOptions)` sum, which includes the system text, messages, and tool schemas but excludes non-serializable admission metadata. Neither byte measure is token accounting. `RunWithActiveRows(ctx, 1)` and `RunWithActiveRows(ctx, 8)` exercise simple and batch fixture shapes. The fixture does not show that PTC improves latency, cost, model routing quality, or production outcomes; those require a live, controlled evaluation.

For only the local Go fixture overhead, run `go test -bench=BenchmarkLocalProtocolOverhead -benchmem ./examples/programmatic`. This benchmark repeats the deterministic stubs and in-memory journal. It is not a provider latency benchmark.

The example journal is in-memory only so the fixture stays self-contained. It demonstrates the runtime call path but does not provide crash recovery; a deployment needs a durable journal implementation.

## Opt-in live model acceptance

`TestLiveProgrammaticSelection` uses the same protected Runtime and context assembler with a real provider. Both direct and programmatic tools are exposed in every case. It tests one active item and eight active items with autonomous strategy selection, then eight items with a required model-written PTC program. Expected answers and program source are not supplied to the model.

Supply `HARNESS_LLM_BASE_URL`, `HARNESS_LLM_API_KEY`, `HARNESS_LLM_MODEL`, and a positive `HARNESS_LLM_MAX_TOKENS` through your private environment. Explicitly select `HARNESS_PROGRAMMATIC_PROTOCOL=responses` for an OpenAI-compatible Responses endpoint; the default uses Chat Completions. There is no automatic protocol fallback or request retry.

```powershell
$env:HARNESS_PROGRAMMATIC_LIVE = '1'
$env:HARNESS_PROGRAMMATIC_PROTOCOL = 'responses'
$env:HARNESS_PROGRAMMATIC_MIN_REQUEST_INTERVAL = '10'
go test ./examples/programmatic -run '^TestLiveProgrammaticSelection$' -count=1 -v -timeout=900s
```

Enabling this test makes paid network requests. Cases run serially. The batched-direct case allows 3 model rounds and 9 tool calls; simple autonomous selection allows 6 and 4; batch autonomous selection allows 10 and 11; both required-PTC cases allow 6 and 11. The second required-PTC case adds tool output schemas while preserving the original case's prompt, data, and budgets. It measures whether an explicit output contract helps the model produce a correct program. The test checks actual fixture calls, each active ID exactly once, final output, and agreement between reported stream usage and session usage events. Only synthetic read-only tools execute. Logged model names are requested configuration, not proof of the gateway's underlying model identity. These small fixtures are acceptance evidence, not a statistical routing-quality or cost benchmark.

### Matched routing-efficiency triad

`TestLiveRoutingEfficiencyTriad` is a separate opt-in Responses experiment. One triad creates a random eight-item opaque dataset, freezes it for three serial arms, and exposes the same prompt and four-tool menu (`program.catalog`, `program.execute`, `fixture.inventory`, `fixture.detail`) to each arm. The only arm-specific input is a persisted profile routing fragment: `sequential_react`, `parallel_react`, or `ptc`. Every arm has a ten-round and eleven-tool-call cap. An arm is attempted once. A local contract failure is recorded and the remaining planned arms continue without retry; only an HTTP, transport, or Responses-protocol failure stops the configured model's remaining work.

It defaults to one triad after the normal live guard is enabled. Set `HARNESS_PROGRAMMATIC_ROUTING_TRIADS` to an integer from 1 through 6 to run independently frozen triads. The six predeclared arm permutations balance every routing arm across all three run positions; evidence records that `arm_position`. The test requires `HARNESS_PROGRAMMATIC_PROTOCOL=responses` so it can retain structural wire observations. Its evidence records only hashes, counts, complete-or-unknown usage totals, timing, context-selection aggregates, and safe Responses request structure. It excludes opaque values, the prompt, model output, tool arguments/results, and submitted PTC source.

Set `HARNESS_PROGRAMMATIC_EVIDENCE_PATH` to a private output directory to retain one uniquely named JSON record per case, including failures. `HARNESS_PROGRAMMATIC_SOURCE_REVISION` can identify the tested source snapshot. Records distinguish Runtime completion from acceptance success and retain reported usage, actual request rounds, pacing versus provider time, request byte counts, and sanitized program diagnostics. Byte counts are not token estimates. Records omit raw prompts, generated source, tool arguments, and credentials. Keep each experimental wave in its own directory and preserve failed attempts when comparing costs.

The optional minimum request interval accepts 0–60 seconds (default 0), is shared across cases, and spaces request starts without retrying failed requests. A provider HTTP, transport, or Responses protocol failure stops the remaining cases. A rate-limited run remains failed; a later intentional run uses a new local fixture.

The 2026-09-09 wave-41 run used one triad per requested model and no retries. Terra passed only forced PTC; its forced sequential and parallel contracts were not followed. Luna passed forced parallel; its sequential arm batched details and failed the sequential contract, while its PTC arm ignored PTC on round one and received HTTP 429 on round two, leaving total usage unknown. Requested names do not prove gateway identity, and provider-reported usage, profile prompts, or a `parallel_tool_calls` flag do not prove stable host routing. See the [routing-efficiency triad record](../../docs/verification/2026-09-09-routing-efficiency-triad.md); it is a single-triad development result, not a global strategy ranking.

### Enforced-route triad

`TestLiveEnforcedRouteTriad` is a separate opt-in Responses acceptance test for the shared route resolver. It creates one random opaque eight-item dataset and runs fresh-session, fresh-journal `auto_first_action`, `direct_only`, and `ptc_only` arms serially. Every arm uses the same prompt, requested model, base profile/system prompt, four-capability universe, ten-step cap, and eleven-call cap. The only arm-specific profile values are `harness.programmatic.route.version=1` and the route mode. Each run calls `internal/executionroute.Resolve` with the default `runexecutor` registry before it executes, so the route wrapper is selected by the shared resolver rather than a test-local adapter wrapper.

Run it only when you intend to make paid model requests:

```powershell
$env:HARNESS_PROGRAMMATIC_ENFORCED_ROUTE_LIVE = '1'
$env:HARNESS_PROGRAMMATIC_PROTOCOL = 'responses'
$env:HARNESS_PROGRAMMATIC_MIN_REQUEST_INTERVAL = '10'
$env:HARNESS_PROGRAMMATIC_ENFORCED_ROUTE_EVIDENCE_PATH = 'D:\private\enforced-route-evidence'
go test ./examples/programmatic -run '^TestLiveEnforcedRouteTriad$' -count=1 -v -timeout=900s
```

The test derives each observed route from every actual model-facing tool schema and the durable session events. `direct_only` must never expose or call catalog/execute. `ptc_only` must expose catalog, then execute, and the fixture inventory plus each detail must appear as an exact program child. `auto_first_action` accepts either a host-locked direct sequence or catalog followed by execute; mixed catalog/direct work is rejected. An arm is attempted once. A logical contract failure writes its evidence and lets the remaining arms run; only an HTTP, transport, or Responses-protocol failure stops the remaining arms.

Set only `HARNESS_PROGRAMMATIC_ENFORCED_ROUTE_EVIDENCE_PATH` for this experiment. Its `harness.programmatic.live-enforced-route/v1` JSON records hashes, the frozen route composition fields, per-round usage and projected tool-menu structure, request/status/latency summaries, and context/execution aggregates. It excludes opaque fixture names, the prompt, model messages, tool arguments/results, generated program source, and credentials. Requested model names identify configuration only; they do not authenticate the provider's underlying model, and provider-reported usage is not billing evidence.

The 2026-09-09 wave-42 run invoked one frozen binary once per requested model, with no retries. Terra completed all three arms: auto locked direct and used 13,366 reported tokens, direct used 13,325, and forced PTC used 14,447; all used three model rounds. Luna completed auto through direct with 13,363 reported tokens, then direct received HTTP 429 on its final request and stopped before PTC. The frozen test had an over-strict wire assertion for absent top-level `instructions` and a zero-tool final request; raw acceptance flags remain false, while a corrected structural rule passes only the completed samples. See the [wave-42 enforced routing record](../../docs/verification/2026-09-09-enforced-routing-live.md). This single development fixture does not promote auto routing or establish a global optimum.

`TestLiveDiverseEnforcedRouteMatrix` adds matched n1 and 2 KiB large-result filter/loop tasks. Wave 43 ran one frozen matrix per requested model with 15-second pacing and no retries. Every auto arm locked direct. Terra auto/direct passed both tasks while both model-written PTC programs failed their effect contract. Luna's large auto and PTC arms passed; PTC used 21.70% fewer reported tokens and 67.00% fewer final-context tokens than auto, showing a real programmatic benefit that current first-action selection missed. Other Luna arms failed the exact answer contract and remain failed because evidence omits answer text. See the [wave-43 diverse routing record](../../docs/verification/2026-09-09-diverse-enforced-routing-live.md).

### Probe-aware v2 route acceptance

`TestLiveProbeRouteV2Acceptance` is a separate, opt-in Responses controlled route comparison for `auto_probe_once` and its `direct_only` control. Each arm starts with exactly one neutral `fixture.inventory` probe. `auto_probe_once` has a fixed three-request/three-step envelope: probe, one Direct/PTC choice, then a tool-free final request. `direct_only` has a bounded ten-request/ten-step envelope so it can batch or split the eight independent details; its final request must make no tool call while the direct menu remains visible. Both arms have a ten-call tool budget. The route-specific execute choice accepts only candidate `selection` plus one safe top-level output `projection`; the host generates and verifies its canonical PTC source. The resolver and normal sequential executor construct the route; the test does not wrap or bypass either one. This control compares these route envelopes and does not isolate a unique causal explanation for any observed difference.

Run it only with intentionally supplied private environment values; the test never reads `llm.txt` and has no automatic retry:

```powershell
$env:HARNESS_ACCEPTANCE_LIVE_PROBE_ROUTE_V2 = '1'
$env:HARNESS_PROGRAMMATIC_PROTOCOL = 'responses'
$env:HARNESS_PROGRAMMATIC_MIN_REQUEST_INTERVAL = '10'
$env:HARNESS_ACCEPTANCE_LIVE_PROBE_ROUTE_V2_EVIDENCE_PATH = 'D:\private\probe-route-v2-evidence'
go test ./examples/programmatic -run '^TestLiveProbeRouteV2Acceptance$' -count=1 -v -timeout=900s
```

This command makes paid network requests. Set the v2 evidence path only when the resulting JSON should be retained. Every v2 evidence record preserves safe per-round token and structural wire evidence, the per-arm model-round and tool-call budgets, and content-free `accounting` plus context-assembly aggregates: call/failure counts, final input bytes/tokens, context limits, and dropped-group count. It never stores messages, tool contents, call or ledger IDs, request lengths, hashes, elapsed timing, endpoint/key material, prompt/response content, arguments, or program source. Its finite `failure_category` is only `none`, `setup`, `runtime`, or `acceptance`. Failed attempts keep the same safe accounting predicates; incomplete usage or a ledger mismatch is evidence of failure, never zero cost or successful reconciliation.

The final 2026-09-09 wave-52 development comparison used evidence v3 and one no-retry auto/direct sample for each requested model. With the observed `128000/4096` assembler limits, both auto arms selected PTC and all four arms passed 8/8 exact-once coverage plus usage/ledger/wire/context predicates. Terra auto used 12,293 input + 234 output = 12,527 reported tokens versus direct 16,645 + 583 = 17,228, a 4,701 (27.3%) difference; Luna auto used 12,293 + 240 = 12,533 versus direct 62,263 + 610 = 62,873, a 50,340 (80.1%) difference. Auto and direct expose different menus and envelopes, requested names do not authenticate the gateway backend, and reported usage is not billing; these single development samples do not establish causality, stability, a global optimum, or a production default. Waves 44–51, including the missing-assembler HTTP 400, 32K wrapper fallback, direct limit, mismatched auto limits, and partial 1/8 direct result, remain part of the evidence. See the [wave-52 probe-aware v2 live record](../../docs/verification/2026-09-09-probe-aware-routing-v2-live.md).

## Opt-in memory/context acceptance

`TestLiveMemoryContextAcceptance` uses the same private environment and evidence settings with the production `memory.recall` capability, an in-process `SliceStore`, the guarded Runtime, and the standard context assembler. Run it explicitly with `-run '^TestLiveMemoryContextAcceptance$'`. Each of two arms allows two model requests and one recall: one store contains a matching fact with an unprompted random value, while the other contains only an unrelated fact. The test checks the answer, exact pairing of the persisted recall result with the final model context, and stream/session usage agreement. It does not test automatic recall routing, durable SQL memory, long-history summarization, memory poisoning, or token savings. A failed arm stops that model's remaining arms; preserve its evidence before any intentional rerun.

`TestLiveSummaryHistoryAcceptance` compares full synthetic Session history, the production `RollingSummarizer` with `LlmSummarizer`, and the local `ExtractiveSummarizer`. The test uses an 8/2 trigger to exercise the archive path; the generic server defaults to 120/60. Each arm allows one answer invocation; only the LLM summary arm adds one summary invocation. Optional `summary` evidence contains both purposes and their total usage, plus fact retention and exact durable-summary/context pairing. Count these totals when comparing cost: the generic per-round list is empty for this specialized experiment. A failed arm stops the remaining arms. These bounded fixtures do not prove long-history quality or amortized savings.

`TestLiveBatchWireAcceptance` compares four-tool and direct-only menus with actual Responses request observations. It reads a cloned request body through `GetBody`, forwarding the original unchanged; evidence retains only flags, counts, hashes, and tool-call names. Removing PTC from the menu is an experimental control, not the proposed product strategy.

`TestLiveProgressiveProgramDisclosure` is a test-only candidate that initially advertises catalog and direct tools, then discloses execute after a paired, successful current-turn catalog result. It compares autonomous n8 with required PTC using output contracts. The underlying Runtime capabilities and permissions stay the same. Both cases retain task assertions; successful disclosure alone cannot pass a program that fails compilation, bindings, effects, or its final answer.

`TestLiveMemoryScopeIsolationAcceptance` adds a development sample with two user scopes containing the same key and lookup token but different opaque values, plus an unrelated same-scope record. Each matching/no-match case permits two model rounds and one recall. It checks scope isolation, exact durable-result/context pairing, an honest `UNKNOWN` on no match, usage accounting, and preservation of the peer record. Its separate evidence schema includes requested model, source revision, usage totals, observation flags, and safe predicates. The prompt specifies a lookup token, so this tests retrieval and answer use rather than autonomous query formulation; the store is in-process, not SQL, and these are not held-out cases.

`python examples/programmatic/summarize_live_evidence.py <evidence-directory>` produces a safe JSON aggregate grouped by source revision, requested model, and case. It includes failed samples and reported partial usage while marking incomplete usage; it never treats empty ordinary rounds as complete zero cost. Summary experiments use their combined summary/answer totals. Their invocation count is separate from ordinary live model rounds and does not prove HTTP request counts. Wire/disclosure sidecars are ignored to prevent double accounting. Unknown or malformed records are counted as skipped, and duplicate physical files are rejected. Review skipped counts before interpreting an aggregate as covering a whole experiment.

New ordinary records add optional invocation reconciliation predicates. The summarizer keeps `ordinary_invocation_evidence` separate from round counts: it reports observed adapter calls, cancellations before entering the adapter, and verified/unverified/unavailable samples. Older records remain unavailable for this stronger check; their historical reported token subtotals are retained. New records with conflicting or incomplete reconciliation retain known reported usage but cannot claim complete accounting. This does not establish the gateway's backend identity or independent billing, and specialized summary/recovery records retain their own accounting contracts.

`TestLiveSummaryRolloverAcceptance` uses a fixed 24-turn synthetic history and three actual Runtime turns: a correction, an acknowledgement, and a current-fact question. It exercises production Extractive/Assembler with a test-only 3/1 rolling threshold. The final prompt omits the opaque answer; the first two replies must be exactly ACK. Safe evidence includes per-run usage and unique invocation checks, each summary's size, effective durable projection, and fact/answer predicates. The total adapter-call cap is three, with no summary-model call. This is a near-capacity local summary test, not a provider context-window or SQL recovery test. The evidence summarizer handles its separate rollover schema and includes failed runs' reported usage.

`TestLiveSQLiteRecoveryContextAcceptance` persists one completed turn, closes SQLite, opens a fresh handle/store, loads the Session and reconstructs Runtime before a second model call. It checks exact restored event/message prefixes, per-run usage, and the final answer after another SQL save/load. The two-call fixture starts empty and uses an opaque fact absent from the final prompt. Its separate SQLite evidence schema is supported by the summarizer. This covers clean reopen of completed sessions, not hard-kill recovery, unknown model outcomes, authorization refresh or PostgreSQL.

`TestLiveLargeDetailProgrammaticBenefit` compares automatic selection, forced batched direct calls, and forced PTC with the same eight-item task, four-tool menu, typed contracts, and runtime budgets. Each detail includes a fixed 2 KiB or 4 KiB irrelevant read-only field; declared output limits include the actual encoded JSON. The 2 KiB control fits all direct results in the default assembler. The 4 KiB case deliberately retains the default context limits: an oversized required current-turn tool group fails assembly before the next model request. Such a failure is not an efficiency success. Evidence records actual fixture effects, reported usage including failed cases, and context assembly observations without persisting result bodies. These are development comparisons, not held-out routing benchmarks.

`TestLiveLargeDetailOutputSizeDisclosure` preserves that pressure setup and adds the exact manifest-derived output bound to the detail tool's initial description. It gives no route recommendation. The historical recording wrapper omits the optional adapter context-limit method, so these tests use Core's 32,768/4,096 fallback. `TestLiveLargeDetailAdapterLimits` separately forwards the inner adapter's actual `ModelContextLimits` and runs 4 KiB auto/batched-direct controls. Evidence records the limits actually received by the assembler; compiler defaults are not provider-certified native limits. See the [routing information and adapter limits report](../../docs/verification/2026-09-09-routing-information-and-adapter-limits.md).

`TestLiveLargeDetailDirectOnlyAdapterLimits` uses the same data and forwarded limits with only inventory/detail exposed, omitting irrelevant program-selection instructions. It verifies two tools in the actual wire requests and complete direct results. This is a separate direct-mode configuration baseline; upstream automatic mode-selection cost is not included.

`TestLiveRepositoryLimitsAcceptance` is a separate repository integration development task. It freezes four allowlisted Go source files in memory, then uses the normal Runtime and a guarded read-only `repo.source.read` capability to obtain evidence for fallback limits, compiler defaults, and the configured output override. PTC remains available without a forced strategy. A private source oracle checks the structured answer and symbol references; source content and expected numbers are not persisted in the result JSON. Its `harness.programmatic.live-repository/v1` record includes source hashes, actual read effects, answer predicates, and ordinary per-invocation accounting. The task is not a blind holdout because its topic has already been investigated during development; it does not establish cheapest routing or broad code-understanding quality.

`TestLiveRepositoryAvailabilityAcceptance` adds complete/compiler-unavailable arms with the same prompt and independent Runtime instances. Unavailable source is omitted from both the tool enum and its in-memory view. Its `harness.programmatic.live-repository-availability/v1` records retain answer predicates and invocation accounting even when acceptance fails. Wave 30 passed only one of four samples; the v1 prompt and symbol oracle also have attribution limits documented in the [availability report](../../docs/verification/2026-09-09-repository-availability-and-strict-gate.md). Preserve these failures when revising the contract; this is a development test, not a held-out benchmark.

The current `repository_availability_v2` fixture clarifies conditional configuration precedence and complete status, retains mandatory declarations, and permits additional real AST identifiers. Additive diagnostics separate null/value matches, required references, and extra identifier existence. Wave 31 passed both complete-source samples but failed both compiler-unavailable samples: compiler numbers were null while precedence remained non-null and status claimed complete. Complete invocation accounting does not turn these quality failures into successful or minimum-cost routes.

`TestLiveMemoryValidityAcceptance` runs fresh, expired and backend-error arms with the same opaque facts and prompt within each requested model. A test-private validity Store filters by scope and entry ID before applying the caller's limit, then the production `memory.recall`, Runtime, journal and assembler handle the actual result. Two adapter calls and one recall are required. Empty successful retrieval and failed retrieval have separate predicates even though both answers must be `UNKNOWN` under this task's contract. `harness.programmatic.live-memory-validity/v1` embeds ordinary invocation accounting and adds payload-free state/context/answer predicates. The summarizer retains failed reported usage and marks incomplete accounting as unknown. This is a development integration experiment with an in-memory store; production TTL, SQL expiry and autonomous fault recovery are not established by it.
