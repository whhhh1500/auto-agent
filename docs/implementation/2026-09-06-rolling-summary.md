# 连续摘要的范围、事实保留和恢复验收

本切片检查默认本地 extractive 摘要。验收将连续三次摘要、服务/连接池重建、SQL 与 HTTP 聊天历史、OTel trace、实际模型请求和回答同时对齐；固定使用 Gemini 3.8 Flash，串行，无自动重试。

## 实现边界

- 保留 core 的 append-only 事件及现有 `context/summary` 替换语义。摘要消息的 `SourceSeq` 是摘要事件序号，其 provenance 是原始覆盖范围，不能把投影首尾的 SourceSeq 当成有序事件区间。
- 在 app 层先计算封闭的归档范围：覆盖归档消息及其摘要来源，包含需要替换的旧摘要事件；不得覆盖未交给 summarizer 的尾部消息。必要时少保留部分旧尾部，仍以真实 user turn 为边界，保留最新 turn。`KeepTail` 是保留数量的上限。无安全边界时在调用 summarizer/写日志前失败。
- 旧摘要使用剩余总摘要预算，不套用普通消息的 1 KiB 限制。保持完整记录和显式省略，不把截断文本假装成完整事实。仍有 12 KiB 硬上限；不承诺无限轮记忆或任意历史事实召回。语义/结构化领域记忆继续由 `ContextSummarizer` 扩展。
- 本轮不增加 core 公共接口或默认额外 LLM 请求。可选 `LlmSummarizer` 的工具元数据及摘要模型调用 usage/trace 汇总问题另列为缺口，不能用本地摘要的结果宣称其已通过。

## 检查

1. 先复现多轮范围错误与大于 1 KiB 的旧摘要事实丢失，再验证缓存投影、从完整事件日志恢复、尾部完整性、失败不追加事件。
2. 用同一初始历史、逐轮新增历史和问题做关闭/开启默认 120/60 摘要的三轮对照。历史种子是明确标注的合成数据，真实调用仅用于三个不同事实的后续提问；不能用上一轮回答重复泄露待测事实。各轮重建服务并核对历史。
3. 报告整个三轮的输入/输出/总 token、请求次数、耗时、摘要事件和 trace。成本结果如无改善也如实保留。跑离线 PostgreSQL 夹具后才请求真实模型。

## 实施结果

已修复连续范围、旧摘要错误套用 1 KiB 限制和跨轮复用 tool ID 配对；取消后不追加摘要。6 次真实请求全部成功，三次连续摘要保留三个分别查询的历史事实，四次服务/连接池替换后事件与投影一致。相对完整历史，输入减少 50.44%，总 token 减少 45.09%，耗时增加 11.59%；七份 JSON、复现回归、基准及证据边界见[实测记录](../performance/2026-09-06-rolling-summary.md)。本次没有扩展 core 接口，也没有把可选 LLM 摘要的用量记录缺口标为完成。
