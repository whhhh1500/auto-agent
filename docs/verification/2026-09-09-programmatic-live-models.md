# 程序化工具调用：真实模型验收

后续证据：[批量协议与输出合同对照](2026-09-09-execution-optimization.md) 发现兼容网关默认禁用批量调用，并记录修正后的成功与失败。本文保留首轮历史样本，不代表当前整体验收状态。

本记录对应 Windows/amd64、Go 1.25.13、本地 `ad90ac0` 加程序化执行及本次验收修复的工作树。测试入口为 `examples/programmatic/live_test.go`。凭据由仓库外配置在运行时注入；不写入本记录或仓库。

结果：六个目标场景中五个取得通过样本；Luna 指定 PTC 场景在两次非限流执行中均未完成。不能将本次验收描述为全部通过。

## 方法与范围

两个请求模型为 `gpt-5.6-terra`、`gpt-5.6-luna`，各串行执行三个案例：一个 active 条目自主选择、八个 active 条目自主选择、八个 active 条目要求使用 PTC。所有案例都暴露相同的两个业务工具与程序目录/执行工具，使用真实 Runtime、保护入口、内存 journal 和默认 ContextAssembler。业务工具只返回本地只读数据。

模型自行读取工具结果；提示词没有正确答案、程序源码或绑定摘要。自主选择案例不规定必须选哪种方式；指定 PTC 的案例要求模型生成程序，并验证全部业务调用都是该程序的子调用。逐项核验每个 active ID 恰好调用一次、inactive 不调用、结果一致、逐轮非零 usage 与 Session 的 usage 事件总数一致。

模型轮次预算依次为 6、10、6，工具次数预算依次为 4、11、11，输出预算为每个请求 4,096 tokens。无自动重试、无协议自动回退。自主批量允许十个模型回合，足以容纳合法的逐项直接调用。

## 首轮失败与诊断

- Chat Completions 路径：两个模型各三个案例均在首轮返回 HTTP 502；六次请求没有返回 usage，也没有工具效果。不能由此归因于 PTC 或推断实际计费为零。
- 对同一入口单独发送最小 Responses 请求成功，响应 `model` 为 `gpt-5.6-terra`，usage 为输入 3,566、输出 5 tokens。该请求仅验证连通性，不属于任务验收成绩。
- 接入项目已有 Responses 适配器后，首轮请求仍失败。补充安全错误分类后确认 HTTP 400；最小工具请求的错误分类命中 `tools/name/pattern/invalid`，定位为 `program.catalog` 等内部带点工具名不符合网关的名称格式。
- 修复放在 OpenAI 协议编解码边界：合法工具名称保持原样，其他内部名称映射为受限字符集的稳定 wire 名，返回调用再还原。当前工具与历史调用都编码；入站只能还原本轮实际暴露的工具。能力目录、PTC source/bindings、Core 身份及 journal 均保留内部名称。
- 并行代码审计发现标准 `event:` SSE 首行未被检测覆盖，已补完整 framing 回归。随后真实请求暴露 `output_text.done` 与 `content_part.done` 被误判重复；另一次最小流式请求确认了完整事件序列，usage 同为输入 3,566、输出 5。解析器现在分别跟踪这两个完成层级，允许相同内容的确认，继续拒绝同类重复和已确认内容的改变。
- Luna 初次批量执行在第 4 个请求收到 HTTP 429，前三个成功请求报告输入 12,827、输出 203 tokens。冷却后以十秒请求起始间隔重建只读 fixture，批量场景通过；紧随其后的指定 PTC 场景首轮又收到 429。这些失败没有自动重试，不能从最终通过的案例中删去它们。

| gpt-5.6-terra | 8 条目，自主选择 | 逐项直接调用 | 10 | 46,698 | 565 | 24.62 秒 |
| gpt-5.6-terra | 8 条目，指定 PTC | 目录 → 程序 → 回答 | 3 | 14,495 | 625 | 15.27 秒 |

耗时来自 Go 子测试，包括本地处理与主动节流；Luna 补测与其他案例不能直接比较延迟。前五行是独立案例的一次通过样本，末行明确记录失败复测；其他失败尝试和连通性请求不计入这些行的 token 合计。没有费率或计费账单，不能据 token 数换算实际费用。

本样本中，两模型在自主批量模式都没有选择 PTC。指定 PTC 的 Terra 样本将模型回合从 10 减为 3，输入 tokens 从 46,698 减为 14,495，输出 tokens 略增。它证明这一任务能受益于程序化执行，但没有证明当前提示策略会自动选择更节省的路径。

## Luna 指定 PTC 失败

排除限流后的第一次执行为三轮，报告输入 14,476、输出 930 tokens，耗时 28.87 秒。模型调用目录与程序入口后给出回答，但 inventory 的实际调用次数为零，验收拒绝；没有因为模型已回答而判定成功。

随后只增加本地结构诊断，不改变模型提示或生产逻辑，限定复测一次。六轮内模型提交五次程序：

1. 程序可编译，但工具集合与 bindings 不一致，返回 `program_bindings_mismatch`。
2. 同一程序的 bindings 修正并与目录一致，但运行求值返回 `program_invalid`。
3. 修改后的程序仍可编译，bindings 正确，运行求值仍返回 `program_invalid`。
4. 另一个较短程序与 bindings 不一致，再次拒绝。
5. 该较短程序随后返回 OK，但运行已达到六个模型回合上限，最终为 `limited`，未完成目标任务。

该记录区分了语法、绑定与求值失败，没有将通用 `program_invalid` 进一步猜测为某一条 IR 指令错误。结构日志只包含源码长度/哈希、布尔校验和固定错误代码，不记录源码、工具参数、模型正文或凭据。两次任务失败以及此前 429 均保留，未通过放宽预算、代写源码或改提示词获得通过。

结论边界：当前证据支持 Terra 在这一个指定 PTC 样例上执行成功，尚不支持 Luna 在同样约束下稳定完成，也不支持两模型能自动选择最省往返的策略。

## 证据边界

这是小规模真实协议与任务验收，不是统计成功率、跨模型排名、最优选路或成本收益证明。网关调用返回的 tokens 是报告用量，缺失不等于免费。Runtime 适配器目前不暴露响应中的实际 `model`；任务结果应标为请求模型，不能凭配置证明网关背后的模型身份。单独连通性请求中的返回模型字段只适用于那一次请求。

本验收不涉及真实通知、生产数据、SQL 恢复或 CodePTC 运行器。之前离线、SQL、硬杀与 race 的证据继续见[程序化执行验收](2026-09-09-programmatic-execution.md)，不能用本次模型调用代替恢复测试。
